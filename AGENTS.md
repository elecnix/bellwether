# Working in this repo

Bellwether is the agent-supervision tool described in the design at `/Users/nicolas/design/bellwether.html`. Read that first. It carries the decisions, the references and the phase plan.

The [README](README.md) is for a person deciding whether to use Bellwether, and `docs/` is for one who has decided. Keep the README to its five questions, and put any detail a user needs into the topic file under `docs/` that covers it.

## Parts and their roles

A parent session runs an adapter: the Pi extension in `src/integrations/pi/`, or the Claude Code MCP channel server in `src/integrations/claude/`. Adapters talk to one daemon per machine. From the definitions in `src/integrations/tools.ts` and the feature table in `src/daemon/features.ts`, the daemon's hello lists the tools a session offers.

Whichever session needs the daemon first starts it detached. It exits once no session stays connected, and no parent's daemon on another machine stays connected through `bellwether relay-bridge`.

Any session connected to a newer daemon gains its tools without a restart. The Claude Code server sends `notifications/tools/list_changed`, and the pi extension registers each new tool. Each adapter offers its own list, less each tool the daemon does not serve, only when the daemon predates the list.

- **Daemon** (`src/daemon/`). It listens on a socket under the Bellwether home, and it is the only process with state. That state covers the registry and the outbox, the relay outbox, and the herdr subscriptions. It starts without the identity variables of the session that launched it. A lock file (`daemon.lock`, which also records the version, protocol, build and entry point, and whether `bellwether daemon` started it in the foreground) keeps a second daemon from starting, so the machine has one daemon for all its children. A client from a newer release, compared by package version and then by protocol, hands the daemon over (`src/daemon/handover.ts`). It first holds `daemon.starting`, so other clients wait. Then it drains the old daemon, which stops taking connections and exits once its calls in flight answer. It waits for the lock to go, and starts its own daemon. Each session connected before the hand-over reconnects to the new daemon, because a daemon serves every protocol back to `MIN_CLIENT_PROTOCOL`, the last bump in `PROTOCOL_HISTORY` that breaks an older peer. A client from an older release never replaces a newer daemon. A client never refuses a daemon on its own: it says hello first. When an older daemon stays, the client speaks that daemon's protocol, and `src/daemon/features.ts` names each operation the daemon lacks, with the release that brought it, once the daemon refuses it. `bellwether drain` drains by hand, `bellwether daemon` runs one in the foreground, and `bellwether doctor` reports where an upgrade stands. [docs/upgrading.md](docs/upgrading.md) gives what a person sees.
- **herdr client** (`src/core/herdr-client.ts`). Newline-delimited JSON on the herdr socket, one connection per request and one held open for the subscription. The subscription waits for the `subscription_started` acknowledgement, and keeps any event that arrives in the same read.
- **Registry** (`src/core/registry.ts`). One JSON file per parent session under `~/.bellwether/parents/`, written only by the daemon. A child record stores its name, kind, host, pane, tab, start time, last status, last `completion_seq`, harness session and transcript path, and keeps them after the child exits. A file written before registry version 2 gains `host: local` on its next write.
- **Watcher** (`src/core/watcher.ts`). It subscribes to `pane.agent_status_changed` for each child pane, plus `pane.exited`, `pane.closed` and `pane.agent_detected`. On connect it subscribes first, reads a snapshot on a second connection, then reconciles. A dropped subscription reconnects with backoff and takes a fresh snapshot. It also sends the answer to a resumed Claude Code session's startup dialog, and starts retirement when a pane exits. A harness that ends and leaves its pane open counts as an exit: herdr releases the agent, or, for a harness herdr never detected, `pane.process_info` shows the shell in the foreground at the one check after the start window.
- **Classifier** (`src/core/classifier.ts`). A pure function of state, clock and observation that turns herdr states into child events, each with its settle time. An open dialog counts as `blocked` whatever herdr reports, and it holds back `idle`, `stuck` and `inactive`. Each child's newest turn the parent heard about, by a report or an `idle` event, sits on its record as `turnNotified` with the pane that ran it, and a watcher seeds the classifier from it, so the parent never hears about one turn twice. [docs/tools.md](docs/tools.md) lists the events.
- **Dialogs** (`src/core/modal.ts`). herdr reports a pi child on an extension's dialog as `idle`. The child's pi extension sends pi's `ui_prompt_start` and `ui_prompt_end` to the daemon as `child_prompt`, which records the dialog on the child record. A local Claude Code child starts with its own settings file (`src/core/claude-hooks.ts`, `~/.bellwether/claude-settings/<child id>.json`, passed with `--settings`), whose `Notification` hook runs `bellwether claude-hook` and sends the same `child_prompt` with `source: claude-code`. When neither has named a dialog, the watcher reads the screen once before an `idle` event, and `detectModal` names the dialog in one line. Bellwether reports a dialog and never answers it, apart from the dialogs in a harness's set in `src/core/startup-dialogs.ts`. For Claude Code, the set contains the two startup questions and two more that Bellwether declines, the read question and the dangerous-rm question. A decline goes on the child record under `decisions`, and the parent's next event names it.
- **Outbox** (`src/core/outbox.ts`). One pending entry per child, where a newer state replaces an older one, apart from an unread report, which stays. At delivery, an unread `blocked` or `stuck` entry drops out once the child has moved on. The adapter marks an entry read when its own message with the receipt enters the parent's conversation. The outbox file stores the read flag and the delivery time with each entry, so a restarted daemon replays only the unread entries, oldest event first. `src/core/notice.ts` orders a backlog by event time and adds a note to an event that arrives more than a minute late. With an alert, the daemon can send the parent's live children, and `src/core/roster.ts` turns them into one line of counts that leaves out the children that alert names (issue #146). `rosterDue` sends a roster only when its line differs from the last one the parent received, and at most once in 10 minutes. The parent record keeps that last line as `rosterSent`. Both adapters compose the text with `src/integrations/alert.ts`.
- **Relay** (`src/daemon/relay-links.ts`, `src/daemon/relay.ts`, `src/core/relay-records.ts`, `src/core/ssh.ts`). The parent's daemon keeps one SSH connection open to each machine that runs one of its children. That connection runs `bellwether relay-bridge` there, and the daemon collects the reports that wait in that machine's relay outbox. `agent_adopt` on a pane there sends `relay-adopt` over the same connection, and the daemon there answers who watches the pane from its registry and its relay records (`src/core/pane-claims.ts`). [docs/remote-machines.md](docs/remote-machines.md) describes the connection, its states and the refusals.
- **Move** (`src/core/move.ts`, `src/core/move-plan.ts`, `src/core/move-endpoint.ts`, `src/core/session-state.ts`). `agent_move` copies a child's harness session to another machine and checks the copy. It then stops the source tab and resumes the session there under the same child id. When the start fails, it starts the child again on the source. The decisions are pure functions in `move-plan.ts`. Each machine computes its own session paths in `session-state.ts`, which the daemon calls directly for its own machine and through `bellwether move-*` over SSH for another. [docs/moving.md](docs/moving.md) lists the refusals and the order.
- **Routes** (`src/core/routes.ts`). A route is a launcher wrapper from this machine's routes file, `~/.config/bellwether/routes.json` or `BELLWETHER_ROUTES`. `agent_spawn`, `agent_restart` and a resume take `via` and `key_file`. The decisions are pure functions: `resolveRoute` refuses a mismatch before any record, and `routeLaunch` builds the argv. `startHarness` in `spawn.ts` types the line at the prompt of a tab the spawn created, then waits for herdr's `pane.agent_detected`. A bare child's line starts with `command`, so the shell never runs a function or alias of the harness's name. The record keeps the route, its tier and the key file's path, never the key. Tests and docs use the synthetic `example-router`, because the repository is public and a real launcher stays in the operator's own file. [docs/routes.md](docs/routes.md) gives the file and the refusals.
- **Spawn, resume, restart and retire** (`src/core/spawn.ts`, `src/core/spawn-resume.ts`, `src/core/restart.ts`, `src/core/retire.ts`). Spawn writes the record, the brief and a Claude child's MCP config, then opens the tab and sends the answers to the startup dialogs. Resume holds a per-child lock under `~/.bellwether/locks/` while herdr decides between a message and a new tab. Retirement records `retireStage` after each removal, so a restarted daemon finishes it without repeating a step. [docs/recovery.md](docs/recovery.md) gives the behavior a user sees.
- **Harness registry** (`src/core/harnesses/`). Each harness has one entry, in a file of its own, named in `index.ts`. The entry gives the launch arguments, where the brief goes and the argument that points at it, and where the session id comes from: herdr, or the harness's own store. It says where Bellwether reads the conversation. It specifies the server or extension that carries the child id, or says why a child of that harness gets none. Last, it lists which states come from an API and which from the screen. Spawn, resume, restart, the watcher, `agent_read`, `relay-register`, the tool list and `features.ts` read the entry, and none of them names a harness. `test/unit/harness-registry.test.ts` fails on a comparison with a harness name outside the registry. `test/integration/harness-registry.test.ts` spawns `fake-agent`, a fourth harness defined only in `test/fixtures/fake-harness.ts`. An entry whose child cannot report declares `reports: { via: 'none', reason }`, and the spawn refuses it before the record. An entry with `since` becomes the feature `agent_spawn.kind=<kind>`, so a client refuses that kind by name against an older daemon. [docs/harnesses.md](docs/harnesses.md) gives what each harness can do.
- **OpenCode** (`src/core/opencode.ts`, `src/core/harnesses/opencode.ts`). An `opencode` child needs OpenCode 2. The spawn writes the brief inside the child's working directory and picks the session id itself. It starts `opencode --standalone --session <id> --prompt <line>`. It then waits for OpenCode's store, `opencode.db`, to show that session with the prompt, and fails with the store's path when the session never appears. `agent_read` and the watcher read the same store. [docs/opencode.md](docs/opencode.md) lists the refusals and what the child can report.
- **Depth** (`src/core/depth.ts`). Each child record holds its ceiling, `maxDepth`, and the depth-0 session's parent record holds the tree's. `agent_request_depth` records a request on the child's record and writes it to the parent's spool as a `needs-input` report. `agent_grant_depth` raises the ceiling within the granter's own. A larger request goes to the granter's parent with `onBehalfOf`, and when the answer comes, it settles each request down the chain. Each grant stays on the record in `depthGrants`. [docs/tools.md](docs/tools.md) gives the rule.

Each adapter sends its session's identity with every call: the herdr pane it runs in, and the child id its spawn gave it. The daemon resolves that identity against its child records, so a `parent_report` goes to the parent whose registry lists the child, whichever process made the call. When no record matches, the error gives the pane and the path of the MCP config file the spawn should have written.

The Claude Code server speaks MCP over stdio, so every log line goes to stderr and stdout carries only the protocol. It exits when stdin closes.

## Layout

```
src/core/          herdr client, registry, watcher, classifier, outbox, spawn, resume, retire, relay records
src/daemon/        the daemon: protocol, server, client, lock, relay, parent service
src/integrations/  the tool list, shared by both adapters, with pi/ and claude/
bin/               the bellwether command and MCP server, run from the sources in a checkout
dist/              the compiled JavaScript that npm publishes, built by `npm run build`
scripts/           the release script, the site build and the phase 0 probe scripts
docs/              user topics, probe results and test briefs
site/              the documentation site's page template and stylesheet
test/unit/         tier 1
test/integration/  tier 2: a fake herdr socket and the daemon
test/lab/          tier 3: a real isolated herdr server
```

## Gates

Run these before a pull request. CI runs the same commands.

```sh
npm run typecheck      # tsgo over src, test, bin
npm test               # tier 1 unit, then tier 2 and 3 integration
npm run doctor         # bellwether doctor against the live herdr
```

`BELLWETHER_TEST_CONCURRENCY` sets how many integration files run at once, and the default is 4. A machine that also runs agents should not have fifteen Node processes competing with them: four files take 37 s at a 532 MiB peak, where fifteen take 22 s at 1 GiB and two take 67 s at 347 MiB.

The documentation site on GitHub Pages comes from `README.md` and the topic files under `docs/`. `npm run site` writes it to `_site/`, and the `pages` workflow deploys it from `main`. A new topic file reaches the site once it has an entry in `PAGES` in `scripts/build-site.ts`.

A release ends only when the deployed site's byline shows the released version, and `npm run release` checks it. Locally, `npm run site` fails on a page whose byline shows a version other than the one in `package.json`.

Prose in Markdown files runs through Vale. The rules are the `ai-tells`, `ai-tells-experimental` and `noslop` packs. The `prose` job runs `npm run check:prose`, which lints `README.md`, `AGENTS.md` and every page under `docs/` with `.vale.ini` as it stands. A warning fails it, as a warning fails the `pr-body` check. Fix the prose, never the level. `npm run check:prose-coverage` then runs Vale again with one added rule that matches once in each file Vale reads, and it fails on a tracked page under `docs/` that Vale skipped. Run `vale sync` once before either. Read `/Users/nicolas/.agents/skills/vale-prose-rules/SKILL.md` before writing docs, a pull request body or a ticket.

## Rules that are not style

- **A session talks to the daemon, not to herdr.** The daemon reads the herdr subscription and stores the registry and outbox for every session on the machine. A tool call from an adapter goes to the daemon, and the daemon sends the adapter its events.
- **Never poll herdr for status.** Status arrives on `events.subscribe`. The only timers are the classifier's settle times and the stuck threshold.
- **Subscribe before the snapshot.** herdr does not replay events, so a subscription opened after a snapshot misses whatever happened between the two.
- **Write the registry record before `tab.create`.** A crash mid-spawn must still leave a trace.
- **Pass the brief through a file.** Each spawn writes it to `~/.bellwether/prompts/<child id>.md` with mode 0600, and the harness gets one line that points at it. herdr refuses an argument with a line break, and a command line shows in `ps`. A spawn that fails removes its record, its brief and its tab, so the parent hears nothing about a child that never ran. A child on another machine gets its brief on that machine: the spawn sends the text on the standard input of `bellwether relay-register` there, and points the harness at that copy. When the copy fails, the spawn fails before it opens a tab. The child's exit, `agent_stop` and a failed spawn remove the copy with `bellwether relay-cleanup`. A resume that brings a prompt writes `<child id>-<n>.md`, and it never overwrites an earlier brief. When the record lacks both a report and a finished turn sent after the newest brief, the resume puts that brief ahead of its prompt. The exit then keeps it on disk (`src/core/brief-history.ts`, issue #132).
- **The daemon keeps the state, and every adapter is a client of it.** The daemon keeps the registry, the outbox and the herdr subscriptions for every session on the machine. An adapter, the Pi extension or a Claude Code MCP server, holds none of them. It sends its identity with every call, as its herdr pane and its child id, and the daemon resolves that against the child records it holds. Never read a parent or a child id from the daemon's own environment, which belongs to whichever session started it.
- **Give each Claude Code child its own MCP server.** The spawn writes `~/.bellwether/mcp/<child id>.json` with mode 0600 and passes it as `--mcp-config=<file>`. The file lists one server, which runs the packaged channel entry with `--child <child id>`. A resume writes it again for the same child id. A child that exits, or whose spawn fails, takes the file with it, as it takes its brief. A child on another machine gets its file from that machine: the spawn runs `bellwether relay-register` there over SSH, which writes the file and a relay record. The relay record has no address for the parent's machine. The spawn refuses a Claude Code child whose own server it cannot write there, because only that server holds the child id. Any other Bellwether server would send its `parent_report` nowhere.
- **Give each Claude Code child one set of Bellwether tools.** `src/core/tool-source.ts` finds each Bellwether server that Claude Code would load for the child on its own. A `bellwether@…` plugin counts when the user, project or local settings enable it. A server counts when its name or command is Bellwether's, in the user, local or project scope. The child's own server wins each time. The child's settings file (`src/core/claude-hooks.ts`, the file's one writer) turns the plugin off with `enabledPlugins`. A server named `bellwether` loses its name to `--mcp-config`. A server under another name loses its name to an entry in the child's MCP config that runs `src/integrations/claude/stand-down.ts`, which doesn't offer any tools. The child record keeps the choice as `toolSource`, and `bellwether doctor` prints one line per harness. The test preload sets `CLAUDE_CONFIG_DIR` to a scratch directory, so no case reads the operator's Claude Code settings.
- **Give each pi child the extension from the running package.** The spawn passes `-e <file>` for the pi extension inside the package that runs the spawn, and sets `BELLWETHER_PI_EXTENSION` to the same file in the tab. A child needs its tools even on a machine whose pi has no Bellwether package. A copy of the extension from the host's pi settings sees the variable and the matching `-e`, so it registers nothing. A spawn that cannot find the file fails before it opens a tab, and the error gives the file name. A child on another machine loads that machine's file, which `bellwether relay-register` prints. So a failed registration fails a pi spawn, and a Claude Code spawn too. An older copy in pi's settings has no guard and makes pi exit on the duplicate tools. While pi's settings list one, the spawn refuses and tells the operator to run `pi install npm:@elecnix/bellwether`. The test preload sets `PI_CODING_AGENT_DIR` to a scratch directory, so no case reads the operator's pi settings.
- **Give a pi child its parent's provider and model.** The pi adapter sends the session's current pair with each tool call, and the spawn passes it as `--provider` and `--model` unless the caller names both. Half a pair fails the spawn before the record, because pi would match it with whatever provider it defaults to. With the pair unknown, the spawn passes neither flag. The reply then gives the provider account that pi chose, read from the child's session file, or until that file exists, the default that pi's settings point to, marked unverified.
- **A spawn fails on a harness that never took its brief.** Until herdr detects the harness, the start checks `pane.process_info` every 500 ms, because herdr doesn't send an event when a program ends in a pane whose shell stays. When the shell takes the foreground back from the harness, the harness has exited. The spawn then fails at once, with the lines it printed. A harness entry can specify the line its harness prints when it stops on a fatal error and stays at its prompt, as pi's `startupFatal` does for `Error: `. The start then waits up to 20 s for the first status. `working` confirms the start, and `idle` or `done` with that line on screen fails the spawn, which quotes the line. A child that hasn't shown a status by then is slow, not dead. The spawn succeeds and its reply says the start is unconfirmed, and the watcher reports the child's exit later. `startingUntil` holds the watcher's events during the wait, so the parent sees a failed start only as the spawn's error.
- **Answer Claude Code's startup dialogs for the person.** Each Claude Code child opens on the development-channel confirmation, because Claude Code loads a `server:` channel only under `--dangerously-load-development-channels`, and that flag always asks. A folder Claude Code has not seen also asks the folder-trust question. The spawn answers both, saying yes to the trust question for any folder, because the operator approves every spawn by default. Some screens number the accepting option, as the channel question does. There, the spawn sends that digit, which selects and confirms the option wherever the cursor sits. Otherwise, the spawn moves the selection toward the accepting option and sends Enter once the screen shows that option selected. The trust question takes this second route, since it doesn't show numbers and ignores a digit. A dialog still on screen after 30 s fails the spawn, with an error that specifies the dialog. While the spawn answers, `startingUntil` on the child record stops the watcher from reporting the child. When a resumed session shows a startup dialog later, the watcher answers it and does not publish a `blocked` event. When a startup question matches no entry, the spawn fails after three reads with an error that quotes it, rather than wait out the 30 s.
- **Settle a child's reads at launch, and decline the rest.** The child's settings file (`src/core/claude-hooks.ts`) names the Bellwether home in `permissions.additionalDirectories` and `sandbox.filesystem.allowRead`, so a Claude Code child reads its brief without asking, whatever the machine's own settings say. Claude Code adds the operator's settings to those lists, so the launch sets the floor and the machine can only add to it. The set is a floor and never a limit: whether a read beyond it asks is the machine's to decide. Claude Code 2.1.332 in auto mode asks only until it sets `hasSeenAutoModeOutsideReadPrompt` in `~/.claude.json`. After that a child reads outside its set without a question, and Bellwether, with no dialog to answer, leaves the record as it was. Never describe the read set to a parent as a limit. Where a read beyond the list asks, Bellwether answers `No, and ask again next time`, which saves nothing to the operator's settings. A shell command Claude Code cannot prove free of a dangerous rm asks too, and Bellwether answers No. Never answer Yes for the operator. A parent widens one child's set at launch with `reads` on `agent_spawn` or `agent_restart` (`src/core/reads.ts`), which refuses the root, the operator's home and anything above it. The record keeps the list, a resume and a restart keep it, and `relay-register` takes it as `--reads` for a child on another machine. A declined read records `outcome: declined` and its `path`, and the event quotes the path, counts a repeat and points the parent at `reads`. Decisions sit on the registry record, which retirement keeps, so an untold decline rides on the `exited` event (`test/integration/retire.test.ts`). Each answer goes on the child record as a `DialogDecision`, written as its Enter goes out, and the parent hears of it once: in the spawn's reply, or in the next event about the child. Bellwether doesn't answer an adopted child: its session started under someone else's settings, and its pane is not the parent's to type into.
- **Close only a workspace Bellwether made.** `agent_spawn` with `workspace: "new"` creates the workspace on the child's machine and starts the child in its root pane, so no empty shell sits beside it, and the child record sets `ownsWorkspace`. The watcher and `agent_stop` close such a workspace once `tab.list` shows it empty. A workspace named by id or label, the parent's own, and any workspace a person made stay as they are, even when empty. herdr closes a workspace with its last tab, so a restart or resume of a child whose workspace herdr has already closed creates another under the same label.
- **The daemon is the reaper.** A child asks the daemon to retire it with `request_retirement`, and a parent's `agent_stop` retires the child it closes. Each records the intent and doesn't remove anything. The watcher cleans up once herdr reports the pane gone, through `src/core/retire.ts`. It refuses unless the worktree is clean and not a main worktree, the default branch, a remote branch or a merged pull request holds its work, and no process works inside it. It never passes `--force` to `git worktree remove`. Bellwether never tells a child to remove its own worktree: a harness that starts each command there fails every command once the directory disappears (issue #143). Never add a separate reaper process, a timer or a witness for it. A child Bellwether adopted, a child on another host, and any main worktree are out of bounds.
- **The daemon is the restarter.** `agent_restart` runs in the daemon, which keeps running after every client stops. A session that restarts itself gets its reply first, and the daemon acts once its turn ends. The request is a field on the record, so a daemon that stops mid-wait arms it again when the session's service starts. Each restart closes the old pane before it starts the new one, so one process runs a session at a time and the person has no old pane to close. For a child, the daemon closes only a pane Bellwether started, and the child comes back in a new tab under the same child id. A parent session's pane closes only when herdr reports the same session id there. The daemon refuses a live agent missing from every registry. An act that began runs to the end, even after closing the caller's pane stops the caller's service. No separate process takes part, and no timer runs beyond the bounded wait.
- **The parent dials out, and the child waits.** The parent's daemon keeps the registry of record. For each machine that runs one of its children, it keeps one SSH connection open. That connection runs `bellwether relay-bridge` there and subscribes the daemon to the reports that wait in that machine's relay outbox. A child's daemon writes each such report to disk. It hands the report to a connected parent's daemon, and it deletes its copy only once that daemon acknowledges it. The parent's daemon accepts each receipt once. After a lost connection, it retries with backoff. `bellwether doctor`, the log, `agent_list` and the inactivity notice all show the state it keeps for each machine. `agent_read` for a remote child goes over the same connection. Never add a connection from the child's machine to the parent's. Use the operator's SSH configuration as it stands, and don't write anything under `~/.ssh`.
- **Use an API before the pane.** When herdr, the harness or its files offer the state Bellwether needs, such as a status event or a transcript, read it there. Reading a pane, or typing into one, is a last resort, because a pane is a rendering of state rather than the state itself, and what it accepts depends on which program holds the foreground. Showing a person a child's screen, as `agent_read` does, is a feature. Reading the screen as evidence for a decision the daemon makes, or typing into a pane when no parent asked, is a fallback. Put a `TODO(api):` comment above each fallback, and in it specify the API, or the change to an API, that would retire it. Put a `Pane feature:` comment above each feature, saying who reads the screen or who asked for the keys. `test/unit/pane-fallbacks.test.ts` fails on a pane read or keystroke with neither comment.
- **Read a pane with its styling.** Claude Code draws a suggested next message faint (SGR 2), and Codex draws its placeholder the same way. herdr's text format drops that styling, so a suggestion reads like typed text. `HerdrClient.paneRead` asks herdr for ANSI and returns a `Screen` from `src/core/screen.ts`. Whether a dialog is up comes first and reads `plain`, every character faint or not, because a dialog dims the options it has not selected. `detectModal` takes both views and needs its selection marker or y/n question solid. A dialog on screen means there is no input box. The answer reads `content`, where every faint character is a space, so Enter goes out only on a solid marker. A screen a parent reads goes through `shownScreen`, which leaves faint text out and ends with `Input box: EMPTY`, `GHOST` or `DRAFT`. Never strip the escapes and guess, and never list a harness's suggestion strings: faint text is a suggestion, whatever it says. [docs/tools.md](docs/tools.md#text-a-childs-harness-suggests) gives what a parent sees.
- **Send input only to panes this parent started.** A parent must never type into a pane it does not own.
- **Wake the parent through its harness.** `pi.sendMessage(..., {triggerTurn: true, deliverAs: 'steer'})` for Pi, `notifications/claude/channel` for Claude Code. Never type into the parent's own pane. A busy pi session takes a steered message after the tool calls in flight, before its next model call. `followUp` holds the message until the whole run ends, and one live run left events nearly five minutes late.
- **Message a child through its session.** A parent's message goes to the child's own Bellwether server or extension, over the daemon connection that adapter opened at its start. The daemon pushes `message`, and the adapter answers `message-ack`. Claude Code takes it as a channel notification, and pi and omp take it through `pi.sendMessage` with `deliverAs: 'steer'`. A harness entry declares its `inbox`. For a child on another machine, the parent's daemon sends `relay-message` over the relay connection to that machine's daemon. The read comes back in that machine's relay outbox as an entry with `messageRead`. `src/core/send.ts` types into the pane through herdr's `agent.prompt` when the entry has none, and also for a blocked child, a session that is missing or silent for 5 s, and a far machine whose connection is down or whose Bellwether predates `relay-message`. The child record keeps each message's path and reason under `messages`. [docs/tools.md](docs/tools.md#messages-to-a-child) gives what a caller sees.
- **Give an adopted session the parent it now has.** A session Bellwether didn't start can still run an adapter it loaded at its start. That adapter says hello with its pane and its harness session, and without a child id. `src/core/adopted-session.ts` finds the parent that adopted the pane: in this machine's registry, or in the claim that a parent on another machine left in the relay records. It names that parent only when the harness session matches the adopted one, because herdr reuses pane ids. The tool list for that session then has `parent_report`. The daemon pushes the new list to each adapter whose hello accepts `tools`, after `agent_adopt`, `agent_stop` or `relay-adopt`. A report from that session goes by its pane: through the registry here, or into the relay outbox under the claim's child id. Never type into an adopted pane to install an adapter. A session without an adapter can't report, and issue #149 records what each harness would need.
- **A delivery marks an event read.** Sending a notification does not prove a turn started. For pi, the proof is the extension's own message, with the receipts in its `details`, at `message_end`. For Claude Code, it is an `attachment` line whose origin is the Bellwether channel. A receipt in a tool result, such as the output of a shell that read the outbox file, leaves the event unread, so a parent that inspects its outbox still gets the notification.
- **Tests run Bellwether on a socket and home of their own.** Every test script loads `test/fixtures/isolation.ts` with `--import`. It sets `BELLWETHER_HOME` and `BELLWETHER_DAEMON_SOCKET` under a temporary root, and throws when a test connects to or listens on anything under the live `~/.bellwether`. `test/unit/isolation.test.ts` fails when a script drops the preload. A test that touches the live daemon or the real registry is a defect. Each test file gets its own home and socket, so `npm run test:integration` runs four files at once. `BELLWETHER_TEST_CONCURRENCY` sets another number, and 1 runs one file at a time. At four the peak is about 530 MiB, and fifteen at once reach 1 GiB to save another 15 s. A case that fails only beside another file has found shared state or a race. Fix the code or the case, and never lower the concurrency. The preload also sets `NODE_COMPILE_CACHE` to `node_modules/.cache/bellwether-test-compile`, and every process a test starts inherits it. Node checks each cached module against its source, so an edited file compiles again.
- **Install the tool a check needs.** Vale, `gh`, `jq` and the rest are part of the work, not an excuse to skip it. Take the version that the dotfiles pin with `mise`, which is how this machine gets Vale 3.20.0, and on a machine without mise install that same release by hand. When an install cannot happen, name what blocked it in the pull request and leave the check failing. A missing binary never counts as a pass.

A fixture mentions a provider, a model or a tier only when it is public or synthetic. This repository is public, and a name from somebody's own setup stays in its history. A synthetic id starts with `example`, `fake`, `test`, `stub` or `mock`. The public providers and model families sit in `scripts/fixture-identifiers.ts`, each with where it is public, and a new entry needs the same proof.

`test/unit/fixture-identifiers.test.ts` and the `fixture identifiers` step in CI enforce the rule. A failure prints the file, the line and the value with all but its first and last characters hidden, because a CI log is public too.

Scripted replies for each parent and child pair come next. The fixtures exist, and the work left is the orchestration that starts Pi and Claude in a lab pane.

The lab removes `HERDR_ENV`, `HERDR_PANE_ID` and `HERDR_SOCKET_PATH` from the child environment, because inherited values point at the live server. It refuses to start when the resolved socket is `~/.config/herdr/herdr.sock`. The lab root is under `/tmp`, because macOS caps a Unix socket path at 104 bytes and a root under the default temp directory exceeds that cap.

A lab case starts real harnesses, and a harness spends the account of any key it finds. So `npm run test:lab` first prints one line listing each provider key, token and cloud credential the shell exported, never its value. Then each lab file's process loads `test/lab/scrub-environment.ts`, which removes them before any case runs. `test/lab/credentials.ts` holds the rule: a name that ends in `_KEY`, `_TOKEN`, `_SECRET`, `_PASSWORD` or `_CREDENTIALS`, among others, or that starts with a cloud SDK's prefix such as `AWS_`. To keep a key, name it in `BELLWETHER_LAB_KEYS`, as in `BELLWETHER_LAB_KEYS=XAI_API_KEY npm run test:lab`. A lab pane still gets a kept key only when its case passes the name to `startLab({ keys })`, and `startLab` refuses a key the run removed, with the command that keeps it. `test/unit/lab-environment.test.ts` runs the `test:lab` command line over probe files to prove both.
